00 · Foundations

The big idea

A GPU database has one hard wall: device memory. "Bigger than GPU" is the architecture that lets BlazingSQL execute queries whose working set does not fit on the GPU — by decomposing a query into small computation units (kernels) connected by smart buffers (cache machines) that can hold data on the device, in host memory, or on disk, and bring it back on demand.

SQL text→ Calcite: logical plan→ JSON plan tree→ PhysicalPlanGenerator→ kernel graph + cache machines→ BlazingTable result

Five components make this work, and this document walks them bottom-up so each layer's job is obvious by the time the next one uses it:

#ComponentOne-line job
1TaskFlow — graph, kernel, portExpress a query as a dataflow graph of independent computation units.
2Cache Machine — CacheMachine, ConcatenatingCacheMachine, CacheData, message, WaitingQueueMove tables between kernels through a queue whose contents may live on GPU, host, or disk.
3BlazingMemoryResource — device, host, diskTrack per-tier memory consumption so the cache knows where data fits.
4Batch processing kernels — simple + complexImplement relational operators as kernels; decompose the heavy ones (orderby, groupby, join) into multi-kernel pipelines.
5PhysicalPlanGeneratorTurn the JSON logical plan into the kernel graph, choosing single-node or multinode configurations.

The TaskFlow model

TaskFlow is the execution substrate: a directed graph where kernels compute and ports name the edges data flows through. Nothing about SQL lives here — it is a general dataflow machine.

the TaskFlow model — redrawn from the original KT sketch

The three nouns

  • Kernel — a node that represents a computation unit in the execution graph. One relational step, one class, one job: pull input batches, compute with cudf, push output batches. Each kernel gets an auto-incremented kernel_id at construction and a kernel_type tag — together these are the 13_7-style ids you see in logs and transformed plans.
  • Port — a name and other properties for each graph edge. Concretely: a map from a port name to the CacheMachine serving that edge. Single-input kernels use a default port; multi-input kernels (join, union) name theirs "input_a"/"input_b"; partitioning kernels fan out over "output_0" … "output_N". Ports are why a kernel never knows who its neighbors are — it only knows names.
  • Graph — owns the kernels and edges, plus a sentinel start node (−1) that source kernels (scans) hang from so execution has a root to walk from.

Declaring a graph — the DSL

The sketch in the original KT is real code. You declare kernels as variables, then describe edges with >>, using [] to pick a port:

// variable declaration                      // graph definition
ral::cache::graph g;
TableScanKernel   a(loader_a, schema_a, ctx);
TableScanKernel   b(loader_b, schema_b, ctx);
JoinKernel        join(join_expr, ctx);      g += a >> join["input_a"];   // ← port name
OutputKernel      out;                       g += b >> join["input_b"];
                                             g += join >> out;
g.execute();

Each += does three things: registers both kernels as nodes, creates the edge's CacheMachine, and registers that cache under the chosen port name on the source's output_ port and the target's input_ port. Producer and consumer now share a buffer without knowing each other. A link(a, b, cache_settings{...}) variant lets an edge request a specific cache flavor (§3).

Anatomy of a kernel

class kernel {                                   // TaskFlowProcessor.h:126
    virtual kstatus run() = 0;                   // pull → compute → push; the whole life
    port input_ {this};                          // named input edges
    port output_{this};                          // named output edges
    std::string expression;                      // its own line of the plan, e.g. "LogicalFilter(condition=[...])"
    const std::size_t kernel_id;                 // auto-increment — the second number in "13_7"
    kernel_type kernel_type_id;                  // enum — the first number in "13_7"
};

struct port {                                    // :78
    std::map<std::string, std::shared_ptr<CacheMachine>> cache_machines_;
};

Note what a kernel carries: its own slice of the query plan as a string. There is no separate expression IR handed around — every kernel re-parses the arguments it needs (sort0=[$1], condition=[...], group=[{0}]) from its expression. The plan text is the contract.

Execution semantics

  • graph.execute() walks the edges breadth-first from the sentinel and launches one thread per kernel, each running run() to completion.
  • run() returns a kstatus: proceed means "my output is complete" — the graph then calls output_.finish(), flipping the finished latch on every downstream cache so consumers can drain and stop.
  • All coordination is blocking pulls on caches: a kernel that needs input simply waits on its input cache. No scheduler, no polling — data readiness is the schedule.
  • All threads are joined before execute() returns; by then the OutputKernel holds the query result.
Why this shape Kernels being ignorant of their neighbors is the whole trick: the same JoinKernel works whether its inputs come straight from scans, from a distributed exchange, or from disk after a spill — because the CacheMachine between them absorbs all of that. Pipeline parallelism falls out for free: scans A and B run concurrently the moment execute() starts.

The cache system model

A CacheMachine is not a cache in the CPU sense — it is a queue whose elements know which memory tier they live in. Producers push GPU tables; the machine decides whether each one stays on the device, moves to host memory, or goes to disk. Consumers always receive a GPU table back.

the cache system model — redrawn from the original KT sketch (L1/L2/L3 around a WaitingQueue)

CacheData — a claim check, not a copy

The element type of the queue is not a table; it is CacheData, an abstract claim check with two obligations:

class CacheData {
    virtual std::unique_ptr<BlazingTable> decache() = 0;   // redeem: bring it back to the GPU
    virtual unsigned long long sizeInBytes() = 0;          // account: what does holding it cost
};
Concrete typeTierWhat it holdsdecache() does
GPUCacheDataL1 devicethe live BlazingTable (cudf columns on GPU)moves the pointer — zero cost
CPUCacheDataL2 hosta BlazingHostTable — the table serialized into host memorydeserializes back into device columns
CacheDataLocalFileL3 diska file path — the table written as an ORC file (/tmp/.blazing-temp-*.orc)reads the ORC back into device columns

Demotion is changing the claim check's type. When the device is under pressure, the machine constructs a CacheDataLocalFile (serialize + write) instead of a GPUCacheData — the GPU memory is released and only the claim check waits in the queue. Promotion is simply decache() at pull time. The consumer's code is identical in every case.

message and WaitingQueue — the conduit

  • message wraps each CacheData with the tier index it landed in and a globally auto-incremented id — "it uses a `message` class to represent a CacheData object and its ID". The id makes batches traceable in logs and, in the mature engine, addressable (pull this message, not just the next one).
  • WaitingQueue is the synchronization core: a mutex + condition variable protecting a FIFO of messages, plus an atomic finished latch. Producers put() and notify; consumers pop_or_wait() — blocking until data arrives or the latch flips. Once finished and drained, pulls return null: that is end-of-stream, no sentinel values, no polling.
  • A second consumer API, get_all_or_wait(), blocks until the latch flips and then drains the entire queue at once — the primitive the concatenating machine (§3) is built on.
Origin note (from the original KT) WaitingQueue is modeled on the communication layer's MessageQueue (comms/include/blazingdb/transport/MessageQueue.h) — the same mutex + condvar mailbox the network Server uses to hand received messages to whoever blocks on getMessage(token). Cache and comms deliberately share one vocabulary: everything is a message in a mailbox, whether it crossed a graph edge or the network.
Version note At tag v0.14.0 the L2 host tier is designed but not built: the CacheDataType enum already reserves CPU, but only GPUCacheData and CacheDataLocalFile exist — pressure demotes straight to ORC. CPUCacheData/BlazingHostTable land in 0.15 alongside the comms host-message work (getHostMessage()).

Cache machines — the types, and the class map

Different edges need different delivery semantics. The machine type — chosen per edge via cache_settings — encodes whether the consumer streams batches, needs everything at once, or reads one lane of a partitioned fan-out.

TypePull semanticsUsed on edges where…
CacheMachine (SIMPLE)each chunk is pulled in batches — one message per pull, blockingthe consumer streams: project, filter, scan → next kernel. The default.
ConcatenatingCacheMachineall chunks are pulled into a single BlazingTable — waits for finish, drains everything, concatenatesthe consumer needs its whole input at once: the final edge into OutputKernel (the query result must be one table), merge stages consuming a full stream.
NonWaitingCacheMachinenon-blocking pop — assumes data is already therepre-filled, single-shot handoffs (the direct-execution path pre-loads a source cache, then runs the kernel).
FOR_EACH (a cache_settings mode)N parallel SIMPLE machines, registered as output_0…N‑1 / input_0…N‑1a partitioning kernel fans out and the merge kernel consumes one lane per partition — the orderby/groupby pipelines.
struct cache_settings {
    CacheType type = CacheType::SIMPLE;      // SIMPLE | NON_WAITING | CONCATENATING | FOR_EACH
    const int num_partitions = 1;            // FOR_EACH: one machine per partition
};
g += link(partition, merge, cache_settings{.type = CacheType::FOR_EACH, .num_partitions = N});

BlazingMemoryResource — device, host, disk

The cache can only place data wisely if something tracks how full each tier is. That is the memory resource's whole job: one implementation per tier, one shared question — "how much is in use, and what is the budget?"

ResourceTracksFeeds the decision
BlazingDeviceMemoryResourceGPU memory consumption vs a budget derived from the device's actual capacitycan this batch stay in L1, or must it demote?
BlazingHostMemoryResourcehost RAM used by BlazingHostTablesis L2 open, or do we go to disk?
BlazingDiskMemoryResourcebytes written as ORC spill filesL3 is the backstop — effectively unbounded

Inside addToCache, the machine walks the tiers in order and takes the first one with room, incrementing that tier's usage; pullFromCache decrements it. The resources are consulted, never in charge — placement policy stays in the cache machine, accounting stays in the resource.

Version note v0.14.0 implements this as two counter vectors inside CacheMachine (memoryPerCache / usedMemory) with a device budget of 75% of free GPU memory (via cudaMemGetInfo) and an effectively-unbounded L3. The named BlazingMemoryResource class family — plus configurable consumption thresholds — is the 0.15 hardening of exactly this model.
05 · Integration

How the abstractions work together

Put one graph edge under the microscope and the whole design appears: a kernel finishing a batch, a cache machine deciding where that batch waits, and the next kernel getting it back on the GPU — never having known it left.

The loop every kernel lives in

kstatus run() {                                          // e.g. SingleSourceKernel
    auto input = input_.get_cache()->pullFromCache();    // blocks; null = end of stream
    if (input) {
        auto output = process(input->toBlazingTableView(), expression, context);
        output_.get_cache()->addToCache(std::move(output));
        return kstatus::proceed;                         // graph calls output_.finish()
    }
    return kstatus::stop;
}

Read the division of labor off that loop:

  • The kernel knows what to compute (its expression) and nothing else. Not who feeds it, not who consumes it, not where its data has been.
  • The port knows which edge — it turns a name into the right cache machine.
  • The cache machine knows where data can afford to wait — consulting memory resources, demoting under pressure, promoting on pull.
  • The graph knows the topology — it created every edge, started every thread, and propagates completion.
Why this makes queries "bigger than GPU" Every intermediate result sits in a cache machine, and every cache machine can demote to host or disk. So the engine's working set on the GPU is roughly one batch per running kernel, not the whole intermediate state of the query. A join whose build side is twice the device memory still runs — its batches queue in L2/L3 and surface one at a time. The price is serialization traffic, paid only under pressure, decided per batch.
Backpressure & end-of-stream, in one breath Consumers self-throttle by blocking on pop_or_wait. Producers never block — the tiers absorb bursts instead (an unbounded queue is survivable precisely because it can spill). Completion cascades: a kernel returns proceed → the graph calls output_.finish() → each downstream cache flips its latch → drained consumers pull null → they finish in turn — until the OutputKernel holds the result and every thread joins.
06 · Integration

Batch-processing kernels

Relational operators come in two weights. Simple kernels are pure streaming — batch in, batch out, no cross-batch state. Complex kernels need global knowledge (order, groups, matches), so each is decomposed into a pipeline of cooperating kernels — this decomposition is what the caches were built for.

Simple kernels

KernelDoes
table_scandrives the data loader — reads this node's files/partitions, pushes tables as they load
bindable_tablescanscan with column pruning and filters folded into the plan line (projects=[[…]], filters=[[…]]) — reads less
projectevaluates expressions per batch on the GPU (arithmetic, CASE, casts, string ops)
filterpredicate → boolean mask → compacted batch
unionconcatenates two streams (UNION ALL)
limittruncates the stream to fetch=[n] rows — distributed, each node keeps its slice of the global n (at v0.14.0 handled inside the sort path; its own kernel later)

Complex kernels — decomposed, per topology

Each heavy operator ships two configurations; the PhysicalPlanGenerator picks one based on the node count. The single-node form skips the network stages; the multinode form inserts them.

Version note These are the mature (0.15+) kernel names the original KT lists. At v0.14.0 the same decompositions exist as SortAndSample/Partition/MergeStream and AggregateAndSample/AggregatePartition/AggregateMergeStream — one kernel set that branches on node count instead of dedicated single-node variants — and join is a whole-table JoinKernel (distribution inside the operator). The pattern is identical: sample → partition → merge, with FOR_EACH caches between partition and merge, and two output ports (output_a data, output_b partition plan) out of the sample stage.
07 · Integration

PhysicalPlanGenerator — JSON plan in, kernel graph out

The bridge between planner and runtime: transform the JSON query plan — a tree — into the execution-graph representation, in different configurations depending on the query execution (single node, multinode). Four moves:

1 · Parse. The relational algebra arrives as a JSON tree, one node per plan line:

{ "expr": "LogicalProject(EXPR$0=[$1], EXPR$1=[$2], n_regionkey=[$0])",
  "children": [
    { "expr": "LogicalProject(n_regionkey=[$0], EXPR$0=[$1], EXPR$1=[CASE(=($3, 0), null:INTEGER, $2)])",
      "children": [
        { "expr": "LogicalAggregate(group=[{0}], EXPR$0=[COUNT($1)], EXPR$1=[$SUM0($2)], agg#2=[COUNT($2)])",
          "children": [
            { "expr": "LogicalProject(n_regionkey=[$3], c_custkey=[$0], c_nationkey=[$1])",
              "children": [
                { "expr": "LogicalJoin(condition=[=($1, $2)], joinType=[inner])",
                  "children": [
                    { "expr": "BindableTableScan(table=[[main, customer]], projects=[[0, 3]], ...)", "children": [] },
                    { "expr": "BindableTableScan(table=[[main, nation]],   projects=[[0, 2]], ...)", "children": [] }
                  ] } ] } ] } ] } ] }

2 · Transform for the topology. Heavy logical nodes are rewritten into their kernel pipelines as strings — LogicalSort becomes the three-line LogicalMerge(LogicalPartition(Logical_SortAndSample(…))) chain, LogicalAggregate its aggregate analog — choosing the single-node or multinode variant by context->getTotalNodes(). Because each rewritten line keeps the original arguments, the new kernels re-parse everything they need from their own expression.

3 · Instantiate. Walk the tree; for each node, match the expression (is_project, is_sort_and_sample, is_bindable_scan…) and construct the kernel. Scans additionally resolve their table to a data loader + schema. Every kernel gets a cloned context stamped with its kernel_id — the ids you see in logs.

4 · Wire. Emit edges child → parent with the right cache per edge:

graph += *scan_a >> (*join)["input_a"];            // binary nodes: ports by child index
graph += (*sample)["output_a"] >> (*partition)["input_a"];   // data
graph += (*sample)["output_b"] >> (*partition)["input_b"];   // partition plan
graph += link(*partition, *merge,  {FOR_EACH, N}); // one lane per partition
graph += link(*merge, *parent,     {CONCATENATING});
graph += link(last_kernel, output, {CONCATENATING}); // the result must be ONE table
Single node vs multinode, concretely Same tree, three differences: (1) the sample stage only emits a partition plan — and the partition stage only consumes one — when totalNodes > 1; (2) FOR_EACH lane count = node count; (3) the distribute/exchange kernels exist only in the multinode configuration. Everything else — kernels, caches, wiring rules — is identical, which is why one generator covers both.
08 · Example

Logical → physical: one query, end to end

The original KT's worked example — a join + group-by over TPC-H customer and nation:

SELECT count(c.c_custkey), sum(c.c_nationkey), n.n_regionkey
FROM customer AS c
INNER JOIN nation AS n ON c.c_nationkey = n.n_nationkey
GROUP BY n.n_regionkey

The logical plan (Calcite output)

LogicalProject(EXPR$0=[$1], EXPR$1=[$2], n_regionkey=[$0])
  LogicalProject(n_regionkey=[$0], EXPR$0=[$1], EXPR$1=[CASE(=($3, 0), null:INTEGER, $2)])
    LogicalAggregate(group=[{0}], EXPR$0=[COUNT($1)], EXPR$1=[$SUM0($2)], agg#2=[COUNT($2)])
      LogicalProject(n_regionkey=[$3], c_custkey=[$0], c_nationkey=[$1])
        LogicalJoin(condition=[=($1, $2)], joinType=[inner])
          BindableTableScan(table=[[main, customer]], projects=[[0, 3]], aliases=[[c_custkey, c_nationkey]])
          BindableTableScan(table=[[main, nation]], projects=[[0, 2]], aliases=[[n_nationkey, n_regionkey]])

Two optimizer fingerprints are worth reading before moving on: (a) SUM became $SUM0 + COUNT($2) + a CASE in the projection above the aggregate — Calcite's AggregateReduceFunctionsRule decomposing SUM so partials merge correctly (null when the count is 0); (b) both scans are BindableTableScan(projects=[[…]]) — BlazingSQL's custom rules folded column pruning into the scans, so customer reads 2 of its 8 columns.

Decoding the ids The original notes label these <kernel_id, context_id>; precisely, the first number is the kernel_type enum value and the second is the kernel's get_id() (a global construction counter, assigned in pre-order as the generator walks the tree — hence 0_1 at the root and 13_8 at the last leaf).
