The QUEST Pipeline Engine — how two phases rewired query execution

A tutorial on what changed: Phase 2 rebuilt the taskflow layer into a push-oriented pipeline engine in the Sirius mold; Phase 1 bridged real queries onto it through a create_plan()-style gate. Together they made the project's namesake — out-of-core query execution — real for the first time. Companion to quest-internals.html, which maps the pre-change architecture.

01 · The change

Before → after: closing the two-engines gap

QUEST used to have two execution stacks that never talked: the callback engine that ran every real query entirely in RAM, and the taskflow engine that owned spilling but was only ever driven by test mocks.

Before — two disconnected engines

Real queries could never spill

QueryBuilder → PhysicalPlan::Execute(callback)
single-threaded recursion, all in RAM
taskflow / cache / memory tiers
⤫ unreachable — only test mocks used it

And even the taskflow engine itself was thread-per-operator: a 6-operator plan = 6 threads + 5 mutex-guarded queues, EOS signaled by an error code, no barrier semantics.

After — one path, gate + fallback

Real queries spill under pressure

QueryBuilder::ExecuteOnGraph()
↓ CreateGraph() — translate or fall back
MetaPipeline::Build → pipelines at blocking ops
↓ FULL / PIPELINE barriers
PipelineExecutor — worker pool, push loop
↓ spill-aware holder at the collector break
CollectorOperator → RecordBatches

Unsupported plan node? CreateGraph errors and the callback engine runs instead — QUEST's own "executor of last resort", exactly Sirius's throw→CPU-fallback discipline.

Why Phase 2 was built first Every later idea depends on real operators flowing real batches through a pipeline runtime: pipelines split the DAG, tasks schedule pipeline work, reservations will gate tasks, spilling serves reservations. Building the engine before the bridge meant the bridge landed on a finished, twice-reviewed chassis — and needed zero changes to it.

03 · The change

Life of a query (the new path)

What happens for FromParquet(f).Where(Col("salary") > Lit(50000)).Select({"id","name","salary"}).ExecuteOnGraph() — step through it.

The push discipline Inside a pipeline, no consumer ever calls upstream. The driver owns the current batch and forwards it through the operator list in plan order (Pipeline::RunTask) — mirroring Sirius's gpu_pipeline_task::compute_task(). Between pipelines, data crosses through a buffered holder and the consumer claims from it — the "pull-like claim at a buffered boundary" that makes the model a hybrid, not pure push.
04 · Deep dive

Operator roles — one class, three jobs

Phase 2 gave every Operator three optional roles, mirroring sirius_physical_operator. An operator implements only the slice it needs:

// execute role — batch-in → batch-out, called by the pipeline driver
//                 in plan order (default: passthrough)
Result<DataBlockPtr> ProcessBatch(DataBlockPtr input);

// source role — supplies batches; EOS is a VALUE (engaged nullopt),
//                not an error code
bool IsSource();
Result<std::optional<DataBlockPtr>> GetNextBatch();

// sink role — receives the pipeline's final batch; blocking operators
//              accumulate state here, then FinalizeSink() flips them
//              into source mode for the NEXT pipeline
bool IsSink();
Status Sink(DataBlockPtr batch);
Status FinalizeSink();

The central invariant: a blocking operator lives in two pipelines

Query: scan → filter → aggregate → project → collect

P0: [scan, filter, aggregate·sink]     aggregate accumulates via Sink()
        │ FULL barrier                 (P1 can't start until P0 finishes)
P1: [aggregate·source, project, ...]   FinalizeSink() flipped it;
                                       GetNextBatch() re-emits

Streaming operators (Filter, Project, Limit) fuse — no holder, no thread handoff between them. Only pipeline breaks get a BatchHolder, and that's exactly where spilling lives.

Where the FULL barrier is actually checked The single most important fact learned from reading Sirius (tasks/notes/pipelines.md): the barrier is checked on the consumer's side and gates task creation — never by the sink, and never by blocking a worker thread. QUEST's executor honors this: a pipeline becomes runnable only when all its FullBarrierProducers() have finished.
05 · Deep dive

Hands-on: the query rebuilt by hand

tests/test_manual_query_walkthrough.cpp is this page as executable code: it recreates FromParquet(f).Where(Col("salary") > Lit(50000)).Select({"id","name","salary"}).ExecuteOnGraph() twice from internal APIs — once with zero machinery, once with every layer explicit — and both times asserts the result equals the real fluent API, batch for batch.

Test 1 — RolesOnlyNoEngine: no Graph, no Pipeline, no executor, no threads

The whole query is a hand-written loop over the four operators' role methods. This loop is Pipeline::RunTask — once you've read it, the pipeline driver holds no mystery:

while (true) {
  auto maybe_batch = scan.GetNextBatch();          // source role
  if (!maybe_batch.has_value()) break;             // EOS is a VALUE (engaged nullopt)

  auto filtered  = filter_role.ProcessBatch(std::move(*maybe_batch));   // execute role
  if (!filtered || filtered->num_rows() == 0) continue;                 // filter ate the batch
  auto projected = project_role.ProcessBatch(std::move(filtered));      // execute role

  collector.Sink(std::move(projected));            // sink role
}

Two subtleties the test surfaces on purpose:

  • Drivers call through Operator&. ProcessBatch is public on the Operator base but protected on SimpleOperator subclasses — implementers override it, only drivers call it. The test binds Operator& filter_role = filter; exactly like the real driver does.
  • Even an engine-less query needs a logical Scan node. Operators consume physical expressions (column indexes, typed eval); CreatePhysicalExpr resolves the names in gt(col("salary"), lit(50000.0)) against an input plan's schema — so the schema provider must exist even when no engine runs.

06 · Deep dive

Spilling — the namesake feature, finally reachable

Step through what happens when the flagship test runs a real Parquet query under a 256-byte CPU budget.

The two fixes that made it real

The Phase 1 review found that ExecuteOnGraph could never spill, for two compounding reasons — both fixed in a65e447:

GapWhy it blocked spillingFix
Total fusionA linear plan fused into ONE pipeline — no BatchHolder anywhere on the path, and MaybeSpill only runs inside holder->Add()CreateGraph puts the collector behind a Full barrier in its own pipeline (Sirius's RESULT_COLLECTOR shape) — final batches always cross a spill-aware holder
Untracked blocksFilter/Project built output blocks with no cpu/disk resources: allocations invisible to saturation, and ToDisk() failed — which MaybeSpill swallows silentlyAll operators stamp blocks via shared execution::MakeTrackedHostBlock; the gate passes the memory manager down
Flagship proof GraphBridgeTest.FlagshipSpillThroughRealOperators: a real Parquet query with filter+project, through the real gate, 256-byte budget → at least one batch arrives at the collector as a DiskBlock, and CollectBatches() materializes everything back (disk→CPU upgrade) with zero row loss.

09 · Reference

What's next — the remaining replication phases

From docs/dev/sirius-replication-plan.md. Phases 1+2 built the chassis; these teach the rest of Sirius's ideas on top of it.

Task-creator hint chain (replication phase 3)
Sirius idea: nothing polls — operators answer READY/WAITING and the creator recurses to the deepest ready producer

Replace "one worker drains one whole pipeline" with data-driven tasks: GetNextTaskHint() → Ready | WaitingForInput, a task = (pipeline, one batch). This also retires the documented ordering-invariant hazard — a consumer waiting for input becomes a non-created task, never a parked worker thread. The counters, status lock, and start_index the executor ships today were built for exactly this.

Memory reservations (phase 4)
Sirius idea: reserve before dispatch; estimate peak from history; clamp to max; OOM ratchets estimates

Tasks secure their estimated peak memory or don't run. Prerequisite honesty fixes: real byte accounting (today's size_in_bytes is a cols × rows × 8 estimate) and macOS RAM detection (hardcoded 8 GB).

Predicate-driven spilling (phase 5)
Sirius idea: downgrade_executor — spill idle batches until "does the reservation fit now?" passes, then stop

Three-state lock on DataBlock (idle ⇄ read_only ⇄ mutable) makes "idle = spillable" safe; a background downgrade worker replaces today's eager MaybeSpill-at-Add.

Blocking operators: Limit → Aggregate → Sort → Join (phase 6)
Sirius idea: partition/merge decomposition — GROUP BY = partition → per-partition agg → merge; ORDER BY = sample sort; JOIN = partition both sides

The seams are ready: roles, barriers, the sink→source flip, and MetaPipeline's blocking-op handling all exist and are tested with mocks. The blocking-op→multi-input relay pipeline (currently rejected loudly) gets built with real joins.

Small debts on the books
Tracked in tasks/todo.md review logs

Layering inversion (cache/batch_holder.cpp → execution/batch_kernels.hpp → physical expressions — split the concat helper down a layer); delete ExecuteLegacy() once the last run()-based operators migrate; vectorized expressions (phase 7) and honest streaming (phase 8) after that.
