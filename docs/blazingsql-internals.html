BlazingSQL Internals — from SQL text to a distributed GPU kernel graph

A guided tour of the engine at tag v0.14.0 — the snapshot behind the "KT Bigger than GPU" document. It traces how a query plan is created (Python → Calcite → RAL), how the plan becomes a graph of kernels connected by CacheMachines, and dissects the physical plan of the hardest operator: a distributed ORDER BY built as a sample sort.

Calcite in-process via jpype/JNI plan = indented text → JSON tree 2 execution paths in runQuery() sample-sort distribution GPU ⇄ ORC-on-disk cache "bigger than GPU" transform present, gated off

02 · Mental model

Life of a query

What happens for bc.sql("SELECT ... ORDER BY ..."), end to end. The plan is born as an indented text tree; it only becomes JSON if the taskflow engine is requested.

Where the plan format changes Calcite returns one string like LogicalSort(...) over LogicalProject(...) over BindableTableScan(...), indentation = tree depth. The legacy interpreter consumes that string directly. Only when use_execution_graph=True does Python's get_plan()/visit() (context.py:462/391) convert it to the JSON {"expr": ..., "children": [...]} tree that C++'s expr_tree_processor parses with boost property_tree. The KT doc's "PhysicalPlanGenerator.h transforms the json query plan" is exactly this mechanism.
03 · Mental model

Two execution paths in one runQuery()

v0.14.0 is a snapshot mid-metamorphosis: the battle-tested recursive interpreter still answers every default query, while the kernel-graph engine — the architecture the KT doc describes — ships beside it behind a flag.

One materialized BlazingTable per plan node, passed up the C++ call stack. Joins/unions find the second child by scanning for the next line at depth 1 (:196-221). No caches, no kernels — but fully distributed via the same operators.

Path B — opt-in (use_execution_graph=True)

One BlazingThread per kernel, tables flowing through CacheMachines (CalciteInterpreter.cpp:376-417). This is the architecture that becomes the whole engine in 0.15+, where it grows batching, a host-memory tier, and PhysicalPlanGenerator.h.

Why the same operators serve both Both paths bottom out in ral::processor::* / ral::operators::experimental::* functions (process_project, process_filter, process_sort, process_aggregate, process_logical_join). Path B merely wraps them in kernels: SortKernel = SingleSourceKernel<process_sort> (TaskFlowProcessor.h:543). The taskflow is a re-plumbing of dataflow, not a rewrite of compute.
04 · Deep dive

Plan → kernel graph: expr_tree_processor

The ancestor of the KT doc's PhysicalPlanGenerator.h lives at TaskFlowProcessor.h:1153-1474. Three moves: parse JSON into a node tree, map each expr string to a kernel, wire kernels with the right cache type per edge.

1 · Kernel dispatch is substring matching

// TaskFlowProcessor.h:1238-1301 (abridged) — make_kernel(expr)
if      ( is_project(expr) )         k = std::make_shared<ProjectKernel>(expr, kernel_context);
else if ( is_filter(expr) )          k = std::make_shared<FilterKernel>(expr, kernel_context);
else if ( is_join(expr) )            k = std::make_shared<JoinKernel>(expr, kernel_context);
else if ( is_sort(expr) )            k = std::make_shared<SortKernel>(expr, kernel_context);
else if ( is_merge(expr) )           k = std::make_shared<MergeStreamKernel>(expr, kernel_context);
else if ( is_partition(expr) )       k = std::make_shared<PartitionKernel>(expr, kernel_context);
else if ( is_sort_and_sample(expr) ) k = std::make_shared<SortAndSampleKernel>(expr, kernel_context);
// ... aggregate variants, LogicalTableScan, BindableTableScan

Each is_* is a find() against a constant (expression_utils.cpp:80-110): "LogicalSort", "LogicalMerge", "LogicalPartition", "Logical_SortAndSample", "Logical_AggregateMerge"… (expression_utils.hpp:94-107). The scan kernels also resolve the table: get_table_index(table_names, extract_table_name(expr)) picks the right data_loader + Schema, and the loader is clone()d per kernel (:1288).

2 · The namesake rewrite: transform_operator_bigger_than_gpu

A sort result can be bigger than one GPU. The fix (TaskFlowProcessor.h:1322-1361): rewrite the plan string itself, splicing one logical node into a three-kernel pipeline before any kernel is built.

LogicalSort(sort0=[$1], dir0=[ASC])
  LogicalProject(...)
    BindableTableScan(...)
findAndReplaceAll(expr,
"LogicalSort", …) ⟶
LogicalMerge(sort0=[$1], dir0=[ASC])
  LogicalPartition(sort0=[$1], dir0=[ASC])
    Logical_SortAndSample(sort0=[$1], dir0=[ASC])
      LogicalProject(...)
        BindableTableScan(...)

The same rewrite handles aggregation: LogicalAggregate → Logical_AggregateMerge(Logical_AggregatePartition(Logical_AggregateAndSample(...))) (:1362-1400). Since each new string still contains the original arguments, the freshly minted kernels re-parse sort0/dir0/fetch or group=[{...}] from their own expression — the plan string is the only contract between planner and kernels.

Gated off at this tag transform_operators_bigger_than_gpu is hard-coded false — both at the struct default (TaskFlowProcessor.h:1220) and at the call site (CalciteInterpreter.cpp:397). So at v0.14.0 a LogicalSort becomes a single SortKernel running the monolithic process_sort; the decomposed pipeline is fully implemented but waiting. In 0.15+ this transform graduates into PhysicalPlanGenerator.h and becomes the only path — exactly the architecture the KT doc describes.

3 · Wiring rules: visit() knows the special edges

// TaskFlowProcessor.h:1439-1471 (abridged)
// SortAndSample has TWO outputs: sorted data and the partition plan
graph += (*child)["output_a"] >> (*parent)["input_a"];
graph += (*child)["output_b"] >> (*parent)["input_b"];
// Partition → MergeStream: one cache PER partition (FOR_EACH)
graph += link(*child, *parent, cache_settings{.type = CacheType::FOR_EACH,
                                              .num_partitions = context->getTotalNodes()});
// MergeStream → parent: concatenate everything into one table
graph += link(*child, *parent, cache_settings{.type = CacheType::CONCATENATING, ...});
// everything else: plain SIMPLE cache
graph += *child->kernel_unit >> (*parent->kernel_unit);

Binary nodes (join/union) get named ports input_a/input_b by child index. Finally execute_plan appends the sink: graph += link(graph.get_last_kernel(), output, {.type = CONCATENATING}) and calls graph.execute() (CalciteInterpreter.cpp:399-405).

05 · Deep dive

TaskFlow & CacheMachine — kernels, ports, and the GPU ⇄ disk cache

The runtime in four types

  • kernel (TaskFlowProcessor.h:126) — a computation unit: virtual kstatus run(), a monotonically assigned kernel_id, and two ports (input_, output_). k["portname"] yields a kernel_pair for wiring.
  • port (:78) — a name → CacheMachine map. Multi-input kernels register "input_a"/"input_b"; PartitionKernel writes to "output_0"… "output_N".
  • kpair / link() (:169-238) — the wiring DSL: a >> b, a >> b["input_a"], link(a, b, cache_settings{...}). Each edge materializes one (or N, for FOR_EACH) cache machines registered on both ports (:406-437).
  • graph (:269) — adjacency sets keyed by kernel id with a sentinel head -1; execute() (:318-356) BFS-walks the edges and launches one BlazingThread per kernel, running run() to completion, then output_.finish(); all threads joined at the end.
Execution model This is thread-per-kernel with blocking pulls — not a task scheduler. A kernel's run() typically does pullFromCache() (blocks on a condition variable), computes via a ral::operators function, addToCache(result), returns proceed. EOS propagates by finish(): the queue's finished latch flips, and blocked consumers wake to a nullptr.

CacheData — where a table physically lives

The KT doc's cache vocabulary maps to CacheMachine.h. A CacheData is a claim check for a table in some tier; decache() redeems it back into a GPU BlazingTable:

The WaitingQueue (:90-165) is the conduit: put() + notify_all, blocking pop_or_wait(), drain-everything get_all_or_wait() (used by the concatenating variant), and the finished atomic as the end-of-stream latch.

addToCache — the tier decision, verbatim

// CacheMachine.cpp:81-106 (abridged)
void CacheMachine::addToCache(std::unique_ptr<ral::frame::BlazingTable> table) {
  for(int cacheIndex = 0; cacheIndex < memoryPerCache.size(); cacheIndex++) {
    if(usedMemory[cacheIndex] <= (memoryPerCache[cacheIndex] + table->sizeInBytes())) {
      usedMemory[cacheIndex] += table->sizeInBytes();
      if(cacheIndex == 0) {                     // tier 0: stay on GPU
        auto cache_data = std::make_unique<GPUCacheData>(std::move(table));
        this->waitingCache->put(std::make_unique<message<CacheData>>(std::move(cache_data), cacheIndex));
      } else {                                  // tier 1+: spill to ORC, off-thread
        std::thread t([table = std::move(table), this, cacheIndex]() mutable {
          if(this->cachePolicyTypes[cacheIndex] == LOCAL_FILE) {
            auto cache_data = std::make_unique<CacheDataLocalFile>(std::move(table));
            this->waitingCache->put(std::make_unique<message<CacheData>>(std::move(cache_data), cacheIndex));
          }
        });
        t.detach();
      }
      break;
    }
  }
}

Budgets come from create_cache_machine (TaskFlowProcessor.h:244-260): tier 0 = gpuMemorySize() * 0.75 — 75% of free device memory via cudaMemGetInfo (GPUManager.cu:11-20) — and tier 1 = INT_MAX with policy LOCAL_FILE. Accounting is a pair of plain counter vectors (usedMemory / memoryPerCache), incremented on add, decremented on pull.

v0.14.0 vs the KT doc's memory model The KT describes BlazingMemoryResource with Device/Host/Disk tiers and CPUCacheData over BlazingHostTable. None of that exists at this tag (verified by grep): the enum already reserves CPU and IO_FILE slots, but only GPU and LOCAL_FILE are instantiated, and there is no host tier between them — spilling goes straight to ORC. The host tier, real memory resources, and config thresholds (BLAZING_DEVICE_MEM_CONSUMPTION_THRESHOLD) land in 0.15+. Also mid-construction honesty: the spill thread is detached fire-and-forget, the threshold comparison adds the incoming size to the budget side, and spilled ORC files are never deleted.
06 · Deep dive

The physical plan for ORDER BY — a distributed sample sort

Sort is the operator that forces every hard problem at once: global order across nodes, data movement, and results bigger than one GPU. BlazingSQL answers with a classic sample sort: sample → global pivots → range-partition → all-to-all shuffle → k-way merge.

Parsing LogicalSort

// OrderBy.cpp:207-223 — given LogicalSort(sort0=[$1], dir0=[ASC], fetch=[10])
std::string limitRowsStr = get_named_expression(combined_expression, "fetch");   // "10" → limit
cudf::size_type limitRows = !limitRowsStr.empty() ? std::stoi(limitRowsStr) : -1;
size_t num_sort_columns = count_string_occurrence(combined_expression, "sort");  // sort0, sort1, ...
for(int i = 0; i < num_sort_columns; i++) {
  sortColIndices[i] = get_index(get_named_expression(combined_expression, "sort" + std::to_string(i)));  // "$1" → 1
  sortOrderTypes[i] = (get_named_expression(combined_expression, "dir" + std::to_string(i)) == "DESC");
}

process_sort then branches on context->getTotalNodes(): single node = logicalSort (cudf sorted_order + gather, nulls hard-coded AFTER, OrderBy.cpp:34-55) plus an optional logicalLimit. More than one node = the algorithm below.

And the merge: sortedMerger (primitives.cpp:296-328) left-folds pairwise cudf::experimental::merge over the received slices — each is already sorted, so the fold yields this node's globally-contiguous sorted range. Concatenating node 0..N-1 outputs in node order gives the total order. A trailing LIMIT becomes a per-node limit via determine_local_limit (OrderBy.cpp:196-205), which exchanges row counts (distributeNumRows/collectNumRows) so each node keeps only min(max(limit − rows_before_me, 0), local_rows).

Why sample sort? Pivots are order statistics of a 10% random sample of every node's sort keys (generateSamplesFromRatio(sortColumns, 0.1), OrderBy.cpp:96-99 — a random gather map, random_generator.cu:65-82). Even sample quantiles ⇒ roughly equal-sized ranges ⇒ balanced nodes without hashing, and — unlike hash partitioning — range ownership preserves order, so the final merge is linear and never re-sorts.

Streaming details

SortAndSample reuses sort() + sample() (OrderBy.cpp:294-348) — the sample/pivot network round-trip only happens when getTotalNodes() > 1.
Partition exchanges ranges via partition_sort (:350-383), then re-samples locally at 25% and cuts each range into 3 sub-partitions with fresh pivots + upper_bound + split (TaskFlowProcessor.h:701-761) — smaller units for the merge to stream.
MergeStream loops until input_0 reports finished, each round pulling one batch per input cache and merging (:781-820) — merge work starts before partitioning ends.
Reality check at this tag Because the transform is gated off, the default v0.14.0 runtime executes LogicalSort as one SortKernel → monolithic distributed_sort. The three-kernel pipeline is real, tested code reachable via build_graph with the flag flipped — and it still carries its scaffolding (debug print_blazing_table_view calls live in MergeStreamKernel's hot path, :804-805). In 0.15+ these kernels mature into BatchOrderByProcessing with single-node variants (LogicalSingleNodeSortAndSample…) — the names the KT doc uses.
07 · Deep dive

GroupBy & Join — the same tricks, different seams

Distributed GROUP BY: aggregate twice, partition once

aggregations_with_groupby (GroupBy.cpp:346-493) runs in five beats: (1) local partial aggregation with cudf groupby (in a background thread); (2) sample the group-key columns at 10% and build pivots with generatePartitionPlansGroupBy — which de-duplicates keys before sorting (primitives.cpp:347-372); (3) sort the partials by key and partitionData at the pivots — range partitioning reused verbatim from sort, not hash partitioning; (4) shuffle with distributePartitions/collectPartitions; (5) re-aggregate the collected partials, rewriting COUNT → SUM so counts of counts combine correctly:

// GroupBy.cpp:477-480
if (mod_aggregation_types[i] == AggregateKind::COUNT_VALID || mod_aggregation_types[i] == AggregateKind::COUNT_ALL){
    mod_aggregation_types[i] = AggregateKind::SUM; // COUNT partials are merged by SUMming
}

Without GROUP BY (aggregations_without_groupby, :215-282) every worker sends its single-row partial to the master, which concatenates and re-reduces. The kernelized form mirrors sort exactly: AggregateAndSampleKernel → AggregatePartitionKernel → AggregateMergeStreamKernel (TaskFlowProcessor.h:827/859/970), where the partition kernel short-circuits when is_aggregations_without_groupby (:872-876).

Join: whole-table at this tag

JoinKernel (TaskFlowProcessor.h:545-588) pulls both inputs entirely from input_a/input_b, normalizes IS NOT DISTINCT FROM to =, splits inequality conditions into an equijoin + residual filter (split_inequality_join_into_join_and_filter), then calls process_logical_join — with a process_filter chaser when a residual exists. Distribution happens inside the operator, not the kernel. The KT doc's PartwiseJoin / JoinPartitionKernel — joining cached partition pairs incrementally — is the 0.15+ evolution of this kernel.

08 · Worked example

The KT query, from SQL to kernels

The exact example from the KT document — a join + group-by over TPC-H tables:

SELECT count(c.c_custkey), sum(c.c_nationkey), n.n_regionkey
FROM customer AS c
INNER JOIN nation AS n ON c.c_nationkey = n.n_nationkey
GROUP BY n.n_regionkey

Calcite returns this optimized plan. Two rules from the Hep program are visible in it: AggregateReduceFunctionsRule decomposed SUM into $SUM0 + COUNT + a CASE (null when the count is 0), and the custom ProjectTableScanRule folded column pruning into BindableTableScan(projects=[[...]]):

LogicalProject(EXPR$0=[$1], EXPR$1=[$2], n_regionkey=[$0])
  LogicalProject(n_regionkey=[$0], EXPR$0=[$1], EXPR$1=[CASE(=($3, 0), null:INTEGER, $2)])
    LogicalAggregate(group=[{0}], EXPR$0=[COUNT($1)], EXPR$1=[$SUM0($2)], agg#2=[COUNT($2)])
      LogicalProject(n_regionkey=[$3], c_custkey=[$0], c_nationkey=[$1])
        LogicalJoin(condition=[=($1, $2)], joinType=[inner])
          BindableTableScan(table=[[main, customer]], projects=[[0, 3]], aliases=[[c_custkey, c_nationkey]])
          BindableTableScan(table=[[main, nation]], projects=[[0, 2]], aliases=[[n_nationkey, n_regionkey]])
