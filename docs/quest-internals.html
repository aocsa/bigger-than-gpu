QUEST Internals — how the CPU engine fits together, and how far it is from Sirius

QUEST is a two-tier (CPU/Disk) batch-processing engine inspired by BlazingSQL's "bigger than GPU" design. This page maps its real architecture as implemented today, walks the life of a query, exposes its central structural flaw, and lines every component up against its Sirius counterpart to derive a learn-by-doing roadmap.

02 · Mental model

Life of a query (the path that actually runs)

What really happens for FromParquet(f).Where(Col("age") > Lit(21)).Select({"name"}).ExecuteCollect(). Note what's absent: no threads, no batch holders, no memory tiers, no spilling.

The contrast with Sirius Sirius converts the plan into pipelines, mints tasks when data is ready, reserves memory before dispatch, and executes on a scheduler. QUEST's physical plan is a recursion of std::function callbacks on the caller's thread — simple and correct, but there is no unit of scheduling, so nothing can be throttled, spilled, reordered, or parallelized.
03 · Mental model

The two engines problem

QUEST contains two parallel execution stacks that never talk to each other. This is the single most important fact about the codebase — and closing the gap is the whole game.

Engine A — runs every query

Callback pipeline

QueryBuilder
↓ builds
LogicalPlan (Scan · Selection · Projection)
↓ CreatePhysicalPlan()
PhysicalPlan::Execute(callback)
↓ recursion, single thread
RecordBatch → callback → collect

Synchronous, in-RAM, one batch per Parquet row group. Never touches BatchHolder, DataBlock, memory tiers, or spill.

Engine B — reached only by test mocks

TaskFlow DAG

graph += scan >> filter >> project
↓ KPair / EdgeConfig
Graph::Execute — one jthread per edge
↓ push / pull
Port → BatchHolder → BlockingQueue
↓ Add → MaybeSpill
DataBlock: HostMemoryBlock ⇄ DiskBlock

Backpressure, saturation thresholds, CPU→Disk spilling — the project's namesake feature. No production Operator subclass exists; only mocks in tests/test_graph.cpp.

Consequence "Bigger than GPU" — running datasets larger than RAM by spilling to disk — is currently impossible for a real query. The spill machinery is unit-tested but dead code with respect to QueryBuilder. Sirius does not have this problem: its create_plan() gate feeds the plan directly into the pipeline/task runtime that owns memory. Phase 1 of the roadmap is the bridge.
04 · Deep dive

TaskFlow & cache — what Engine B gives you

Engine B is genuinely good architecture, closely mirroring Sirius/BlazingSQL concepts. It just needs real operators and a bridge from the planner.

The DSL and the graph

*graph += table_a >> join["input_a"];
*graph += table_b >> join["input_b"];
*graph += link(sort, merge, EdgeConfig::Concatenating());
graph->Execute();   // BFS; one std::jthread per outgoing edge
  • Graph stores edges/reverse-edges keyed by operator id; sources hang off sentinel node -1. Execute() BFS-walks, launching a thread per operator run.
  • Operator is the node base: run() + can_you_throttle_my_input(); SimpleOperator adds the pull → ProcessBatch() → push template loop.
  • Port maps named slots ("input_a", "input_b") to IBatchHolders — the same shape as Sirius's "default"/"build" repository ports.

Backpressure

Producers call WaitIfSaturated(): a condition variable blocks until batch_count/current_bytes fall under the edge's flow_control_*_threshold. Consumers block on BlockingQueue::Pop(). Defaults are SIZE_MAX (off) unless EdgeConfig::with_flow_control() is used. This is a coarser cousin of Sirius's barrier types (FULL/PARTIAL/PIPELINE) — but QUEST blocks threads, where Sirius gates task creation.

Stub alert ConcatenatingBatchHolder::ConcatenateAll errors on more than one block (batch_holder.cpp:213) — concatenating edges, which aggregations and final sinks need, are effectively broken for multi-batch inputs.

06 · Deep dive

Parquet & the data plane

QUEST ships a from-scratch Parquet reader — Thrift compact-protocol decoder included — which is a genuinely instructive artifact. Supported today:

  • Types: Boolean, Int32/64, Float, Double, ByteArray, FixedLenByteArray, Int96 (raw bytes, no timestamp semantics). No Date/Timestamp/Decimal logical types — annotations aren't even parsed.
  • Encodings: PLAIN + dictionary (PLAIN_DICTIONARY / RLE_DICTIONARY). DELTA_* and BYTE_STREAM_SPLIT silently misdecode (fall through as plain).
  • Compression: Snappy + uncompressed only. ZSTD/GZIP/LZ4/Brotli → UnsupportedEncoding.
  • Shape: flat schemas only — max_rep_level hardcoded 0, group elements dropped in BuildSchema.
  • Batching: one RecordBatch per row group; batch size is whatever the file says, not configurable — versus Sirius's split provider coalescing to a byte target (512 MB) with prefetch and stats-based row-group pruning.

Data currency: RecordBatch = Schema + typed ColumnVectors (bit-per-value null bitmaps, 1 = valid). Spill format: RecordBatchSerializer, magic "QRBT" — beware it encodes types as std::variant::index() (append-only ABI, same footgun class as Sirius's AST variant) and it throws, diverging from the project's Result convention.

08 · vs Sirius

What to build — the learn-by-doing roadmap

Eight phases, ordered so each one teaches a core Sirius idea at CPU scale and leaves the engine strictly better. Full details, exercises, and Sirius file references live in docs/dev/sirius-replication-plan.md.

Bridge the two engines
Sirius idea: create_plan() gate → runtime

Write CreateGraph(PhysicalPlan) → Graph: real TableScan/Filter/Project operators that wrap the existing Exec nodes and move RecordBatches through BatchHolders. Unsupported node → fall back to the callback engine (QUEST's own "CPU fallback"). After this phase a real query can spill for the first time.

Pipelines, not threads-per-operator
Sirius idea: meta-pipeline build · blocking ops are sink of one pipeline, source of the next

Split the operator DAG into pipelines at blocking operators. Streaming ops (filter/project/limit) fuse into one pipeline; a blocking op ends it. Introduce barrier semantics on edges: FULL (consumer waits for producer pipeline to finish), PIPELINE (pure streaming).

Data-driven tasks + scheduler
Sirius idea: task_creator hint chain · nothing polls, work exists only when data does

Replace jthread-per-operator with a worker pool. Each operator answers GetNextTaskHint() → Ready | WaitingForInput; a task creator recurses into producers to find the deepest ready work; a task = (pipeline, one input batch).

Memory reservations
Sirius idea: reserve before dispatch · estimate peak from history · clamp to max

Tasks must MakeReservation(estimated_peak) before running. Default estimate 2× input bytes; keep a per-pipeline ring of (estimated, actual peak) and correct with the observed ratio. Fix accounting: measure real batch bytes, not cols × 8.

Predicate-driven spilling + batch locks
Sirius idea: downgrade_executor · idle ⇄ locked batch states · spill until the reservation fits

Give DataBlock a three-state lock (idle/read_only/mutable); only idle blocks are spill candidates. A background downgrade worker serves RequestDowngrade(predicate) requests, spilling idle blocks until make_reservation_or_null succeeds. Upgrade lazily at next use.

The blocking operators: Limit → Aggregate → Sort → Join
Sirius idea: partition/merge decomposition — GROUP BY = PARTITION → per-partition agg → MERGE; ORDER BY = sample sort; JOIN = partition both sides → build/probe

One operator at a time, each with logical node, physical node, taskflow operator, and spill support. Hash aggregate first (it forces cross-batch state), then 3-phase sample sort, then partitioned hash join with the left=probe/right=build convention.

Vectorized expressions
Sirius idea: one evaluator, pluggable strategies (MATERIALIZE vs AST) · plan-time expression translation

Kill row-at-a-time GetValue(i): evaluate column-at-a-time over contiguous typed arrays, null bitmaps as words. Keep the row path as a fallback strategy — mirroring MATERIALIZE vs AST_INTERPRET. Also fixes: arithmetic exprs currently aren't even plannable (CreatePhysicalExpr misses them), int64 precision loss via double upcast, no type promotion.

Real streaming + scan improvements
Sirius idea: exchange_channel (bounded, byte-capped, close-then-drain EOS) · split coalescing · predicate pushdown

Make StreamingQueryBuilder honest: pull batches through the graph with backpressure instead of buffering everything. Evolve BlockingQueue toward the exchange-channel contract (item + byte caps, oversized-batch rule, on-close callbacks). Scan: configurable batch bytes, row-group pruning from stats, predicate pushdown.
