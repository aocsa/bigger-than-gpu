Two operators, one complete exchange

Both halves of a distributed exchange are now in the tree: STREAMING_SOURCE (merged as be412ecc, PR #1094) turns "batches arriving from another node" into an ordinary pipeline source; STREAMING_SINK (PR #837, 96e55d8f, ready for merge) registers each outgoing batch in a shared repository — zero-copy, spillable — and forwards a lightweight handle to the channel. This page walks both operators, the exchange_channel they share, the contracts their 2,300+ lines of tests lock in, where they plug into the StarRocks compute-node plan (#826, #835–#841), and what still separates an in-process exchange from a real distributed one.

01 · What landed

Two PRs, a complete exchange edge

The source merged first, sealing the consumer side and the channel contracts. The sink arrives as a PR ready — the producer twin that closes the local-exchange loop before network and session wiring land in #838/#839.

PR #1094 · be412ecc · merged → devThe consumer half

Adds exec::exchange_channel (MPMC, bounded by items and bytes, close-then-drain EOS, re-arm callbacks) and sirius_physical_streaming_source — a source operator marking the bottom edge of an intermediate pipeline fragment. New STREAMING_SOURCE enum value, docs, and two test suites ([exchange_channel], [streaming_source] SRC-1…21, BUG-1/2) pin the contracts including two key lessons: admission must inspect the candidate handle (not just channel fullness), and EOS must wake the pipeline even when no task is in flight.

PR #837 · 96e55d8f · PR readyThe producer half

Adds sirius_physical_streaming_sink — a CONCAT-shape operator (is_source + is_sink) heading its own pipeline. It pops batches from an input port, registers each in an output shared_data_repository (making it spill-visible to the downgrade executor), and pushes a lightweight {batch_id, size_bytes} handle to the exchange channel. Key invariants: zero-copy (no host clone), backpressure as admission (full channel → _pending queue → WAITING hint, workers never block), and flush-then-close EOS (deferred via _close_when_flushed if pending isn't empty). 990 lines of tests cover all scenarios.

The one-sentence thesis Pipelines used to be connected only by ports (local data repositories). These two PRs add a second kind of edge — a channel whose producer is outside the local plan — and teach the engine to schedule, flow-control, and finish against it in both directions. That is precisely one complete StarRocks exchange, minus the network.

03 · Mechanics

The exchange channel: bounded, handle-based, close-then-drain

One header, four verbs — push, pop, close, and the callbacks that re-arm the scheduler. Every rule below is enforced by a test you can run.

struct exchange_batch_handle {
  uint64_t batch_id;       // repository batch id — repo is the owner of record
  std::size_t size_bytes;  // size estimate captured at registration
};

exchange_channel::config{ .capacity_items = 4,     // required, > 0
                          .capacity_bytes = 50 };  // 0 = no byte bound

Two API tiers, one reason

Engine workers use try_push / try_pop only — a GPU worker must never park on a queue; when the channel can't serve it, task creation simply stops. Blocking push() / pop() exist for the wrapper/test side, where a dedicated receiver thread may legitimately wait for headroom.

Callbacks: two different events

on_push/on_pop mean "data availability changed" — the future session (#839) uses them to re-schedule task creation. on_close means "the stream ended" — a different consumer entirely (pipeline-completion re-evaluation), firing exactly once, outside the lock, single-slot, last-setter-wins. The owner must clear a callback before its captured object dies.

The bug commit 2 fixed — in one line full() answers "is the channel at its bound right now?" — it cannot see the incoming handle. Gating admission on it let cumulative pushes cross the byte bound (40 queued + 40 incoming vs a 50 bound → 80 queued). Flow control that ignores the thing being admitted isn't flow control. Admission and state queries are now separate functions with separate jobs.

The streaming source: a source with an invisible producer

Every Sirius source answers the task creator's question — "can you produce a task?" — through get_next_task_hint(). This operator's answer is special because its producer lives outside the local plan.

Why WAITING{nullptr} is the interesting cell For every other operator, WAITING_FOR_INPUT_DATA carries a producer pointer and the task creator recurses upstream (get_operator_for_next_task hint chain) until it finds someone READY. The streaming source's producer is another node — there is nothing local to recurse into, so it returns nullptr and the request is dropped on purpose. The contract: a future push must re-schedule via the session (#839) — edge-triggered wake-up instead of chain-walking. Until #839 lands, tests poll.

The rest of the operator contract

The dtor must clear the slot — the channel is co-owned by the producer side and can outlive the operator; a stale callback would fire on a dangling this.

The GPU twist: queued batches can spill — and self-heal

SRC-14, step by step

  • Producer registers a GPU batch in the repo, pushes its handle.
  • While queued, the downgrade path converts the batch to HOST tier — legal precisely because the repo, not the channel, owns it.
  • Consumer pops the handle; gpu_pipeline_task runs prepare_for_processing(gpu_space) — the standard colocation gate every task input passes through.
  • The batch converts back to GPU; execute() returns values intact.

Why this matters for the exchange design

Exchange buffers are where memory pressure concentrates — a slow consumer means queued data. StarRocks buffers serialized chunks in host RAM and can throttle senders; a GPU engine holding queued batches in device memory must keep them spillable or a stalled exchange becomes an OOM. This is the "option A" memory design from your onboarding (#840): exchange batches live in the shared cuCascade repository so they spill like any other batch.

04b · Mechanics

The streaming sink: the producer twin

sirius_physical_streaming_sink (PR #837) is the operator that closes the local exchange loop. It heads its own single-operator pipeline as a CONCAT-shape (both is_source() and is_sink()), pops batches from an input port, registers them in an output repository, and forwards handles to the channel — never blocking a worker.

Zero-copy emit: why the order matters

// sink() per batch — the core invariant:
output_repository->add_data_batch(batch);           // 1. register first — spill-visible now
auto handle = exec::exchange_batch_handle{
  .batch_id   = batch->get_batch_id(),
  .size_bytes = batch->get_data()->get_size_in_bytes()
};
if (!_output_channel->try_push(handle)) {           // 2. push handle only
  std::lock_guard<std::mutex> lk(_pending_lock);
  _pending.push_back(handle);                       // 3. park if full — never block
}

No data leaves the repository. No serialization. The batch is idle and spill-visible from step 1; the consumer resolves it later with pop_data_batch_by_id(handle.batch_id).

The sink's hint table

Stateget_next_task_hint()Why
_pending non-empty or channel full WAITING{nullptr} Stalled on consumer; no new tasks until the consumer pops headroom. Worker never blocks.
input port non-empty, channel has room READY{this} Mint a task: pop + register + try_push.
port empty, upstream pipeline finished std::nullopt EOS: on_finalize_operator() flushes pending and closes the channel.
port empty, upstream still running WAITING{upstream_op} Propagate the hint chain up to the nearest READY operator.

Flush-then-close EOS

on_finalize_operator()

  • Calls try_flush_pending() — drains _pending FIFO into the channel.
  • If _pending is now empty: _output_channel->close() immediately.
  • If handles remain: sets _close_when_flushed = true and returns — the close is deferred to the next successful flush triggered when the consumer pops headroom.

The deferred-close race

The consumer's hint loop calls try_flush_pending() on every tick. The last try_push that drains _pending also checks _close_when_flushed and fires close() — outside the consumer's lock, so no deadlock. This is the same "fire outside the lock" rule the source's on_close callback follows.

Known gap (deferred to #839): there is no re-arm path yet. When a consumer pop opens channel headroom, the sink's WAITING state persists until the task-creation loop polls again. The session will add an on_pop callback to call schedule(sink).

CONCAT shape: why is_source() and is_sink() are both true An ordinary sink operator is the terminal of a pipeline — it receives batches from upstream via sink() but produces nothing further locally. The streaming sink is different: it also acts as a source for task creation (the task creator queries its hint to decide whether to pop from the input port and run a sink task). This CONCAT shape means the operator heads its own single-operator pipeline. is_source() = true puts it in the hint-walking chain; is_sink() = true connects it to the upstream pipeline's port.

Spill self-heal — same guarantee as the source

Once registered in the output repository, a queued batch can be downgraded to HOST tier by the downgrade executor — no different from any other idle batch. The consumer side's prepare_for_processing(gpu_space) (inside gpu_pipeline_task) brings it back to GPU when the task runs. The zero-copy sink design is what makes this possible: if the sink owned the data directly (e.g., a host clone), the batch would be stranded outside the spill-visible repository.

07 · Distributed

The biggest structural gap: every verb is still a function call

The channel has three verbs — admit, wake, end. In this PR each is a mutex-guarded function call inside one process. In a distributed exchange each must become a protocol: a message that can be delayed, reordered, duplicated, or lost.

Gap detail

Pick a gap

Click a gap — what exists today, what distribution demands, and where the answer lives.
The verdict The deepest gap is EOS. close() is anonymous and single-shot: any caller ends the stream for everyone, and the API has no notion of how many producers must finish first. A shuffle gives every fragment N upstream senders; StarRocks solves it with a counted-sender protocol (receiver finishes at remaining-senders = 0, sender count wired from the plan). Your onboarding flags exactly this as open question Q11 — EOS across nixl/bRPC and where the sender count comes from. Flow control degrades gracefully if you get it slightly wrong; EOS does not — it's the difference between a query that finishes and one that hangs (commit 3 was this lesson at single-node scale).

08b · What's next

Stream session support (#839)

The local exchange is in place. The next piece is the glue that wires it to the outside world: a session that builds a streaming plan, starts it on the existing task scheduler without blocking the caller, and exposes a clean API to the Rust wrapper.

The core idea The session is the public entry point for streaming computation. It takes a plan, feeds it to the GPU executor as an ordinary set of operators, and exposes four verbs to the wrapper — push, close_input, pull, wait — routing each by stream_id. No new thread pool. No new scheduler. The exchange operators run inside normal gpu_pipeline_tasks on the same workers that run compute.

The four verbs

VerbDirectionWhat it doesContract
push(stream_id, batch)Wrapper → source Registers the batch in the owning shared_data_repository, pushes its handle into the exchange_channel for the source identified by stream_id, and fires schedule(source) to wake task creation. Non-blocking for the caller; the channel's admission rules apply. Returns false (or blocks on the wrapper's dedicated thread) when the channel is full — that backpressure signal is what throttles upstream senders via the nixl/bRPC path.
close_input(stream_id)Wrapper → source Signals that no more data will arrive on this stream. In-process today: calls channel.close() for the matching source. Distributed requirement: the call must be counted against a sender set (open Q11) so the stream ends only when all senders have signalled EOS. Idempotent locally; the counted-sender wrapper is the work #839 owns.
pull(stream_id)Sink → wrapper Pops a handle from the sink's output channel and resolves it via output_repository.pop_data_batch_by_id(handle.batch_id). Each pop also calls try_flush_pending() on the sink — this is the indirect re-arm that drains the sink's backlog (#837 documented known gap). Non-blocking; returns nullopt when the channel is empty. A wrapper thread may call blocking wait(stream_id) instead.
wait(stream_id)Sink → wrapper Blocking variant of pull — parks the wrapper thread until the output channel has data or is drained. Safe because wrapper threads (not GPU workers) may park; the engine workers always use non-blocking paths. Returns nullopt when the channel is drained (EOS). The wrapper drains remaining results and frees the session.

Plan construction — Substrait first, builder API later

What the session builds

  • Takes a plan description (initially via the existing Substrait translation path — no new parser needed).
  • Instantiates the physical operator tree: leaf fragments get their normal scan; intermediate fragments get a STREAMING_SOURCE at the bottom and a STREAMING_SINK at the top.
  • Creates and wires the exchange_channels and shared_data_repositorys between operators.
  • Calls task_scheduler.submit(plan) — non-blocking; the scheduler manages execution from here.

Routing by stream_id

The session maintains a map<stream_id, exchange_channel*> for inputs and a parallel map for outputs. Each source and sink is keyed by the stream identifier that the FE plan assigns (the same identifier that appears in TExecPlanFragmentParams and flows through the Substrait translation).

Error handling: unknown stream_id on push/pull throws or returns an error status — the session never silently drops data. Recovery from mid-stream errors (e.g. a lost upstream sender) is an open design question tracked under #839.

Why Substrait first, not a builder API An operator builder API would be the cleanest long-term interface — session.source(id), session.sink(id), session.connect(source, filter, sink). But building it correctly requires settling the exact operator construction signatures, port wiring conventions, and memory-space injection patterns — decisions that will crystallize while implementing #839 rather than before. Reusing Substrait translation means the session has a working plan path on day one; the builder API can be extracted as a refactor once the patterns are clear.

The re-arm race #839 must solve

Both operators today have a known gap: the task-creation loop polls rather than being woken. A push that lands while the source's WAITING hint is being dropped must not be lost. The session owns the edge-triggered fix: on_push → schedule(source) and on_pop → try_flush_pending() + schedule(sink). The race is the same one StarRocks solves with driver event observers + a polling backstop — level-triggered insurance over edge-triggered speed.
