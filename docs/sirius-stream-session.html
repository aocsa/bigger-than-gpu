Sirius design deep dive · §3 · exchange-design.md · issue #839

The session calls four verbs; the engine handles the rest

The stream session is the single public entry point for streaming computation. It builds a plan, starts it on the existing task_scheduler without blocking, and exposes push / close_input / pull / wait to the Rust wrapper. The streaming source and sink are ordinary Sirius operators — no dedicated thread pool, no separate subsystem. The bounded channel between them is the only hand-off queue and the entire flow-control mechanism.

01 · What the session is

One class, three responsibilities

The session is not a thread pool or a scheduler. It is a plan builder and an API surface: it wires operators to channels and exposes those channels to the wrapper.

responsibility 1Build the streaming plan

Translate the incoming fragment description (Substrait, eventually #841) into physical operators. Leaf fragments get their normal scan; intermediate fragments get a STREAMING_SOURCE at the bottom and a STREAMING_SINK at the top. Wire the operators, repositories, and channels together.

responsibility 2Start non-blocking

Submit the plan to the existing task_scheduler and return immediately — the caller is never blocked waiting for the plan to run. The scheduler drives execution asynchronously; the session doesn't own the execution loop.

responsibility 3Expose the four verbs

Translate push / close_input / pull / wait calls from the Rust wrapper into channel operations, routing by stream_id. The channel itself (exposed over the cxx FFI) is the only boundary between wrapper and engine.

What exists today — what the session replaces Today, operators source data only from scans (bound to a split_connector) or a pre-materialized COLUMN_DATA_SCAN, and a query's result is fully materialized into a ColumnDataCollection (sirius_physical_materialized_collector in src/op/sirius_physical_result_collector.cpp). The stream session replaces both ends with channel-backed streaming, reusing the operator interface that already exists (execute / sink / is_source / is_sink / get_next_task_hint / get_next_task_input_data in src/include/op/sirius_physical_operator.hpp).

The session's internal map

The session maintains two maps keyed by stream_id — one for input channels (sources) and one for output channels (sinks). Each stream_id is assigned by the FE plan and flows through the Substrait translation (#841). The same session can host multiple concurrent streams within one fragment — one source per upstream sender, one sink per downstream destination.

// Conceptual internal state — not the final API
struct stream_session {
  // input: wrapper → engine (one channel per upstream stream)
  std::map<stream_id_t, shared_ptr<exchange_channel>> _input_channels;
  std::map<stream_id_t, shared_ptr<shared_data_repository>> _input_repos;

  // output: engine → wrapper (one channel per downstream destination)
  std::map<stream_id_t, shared_ptr<exchange_channel>> _output_channels;
  std::map<stream_id_t, shared_ptr<shared_data_repository>> _output_repos;

  // operators — ordinary sirius_physical_operator subclasses
  std::vector<unique_ptr<sirius_physical_operator>> _operators;
};

// Step 1: register in the owning repository — spill-visible from this point on
auto batch_id = input_repo->get_next_data_batch_id();
input_repo->add_data_batch(batch);                        // owner of record

// Step 2: push the lightweight handle to the channel

                                           .size_bytes = batch->get_size_in_bytes() };
if (!input_channel->try_push(handle)) {
  // channel full — wrapper thread may block on the blocking push() overload,
  // or back off and signal not-ready upstream
  input_channel->push(handle);    // wrapper thread parks here — never an engine worker
}

04 · The wrapper⇄engine boundary

The channel is the boundary

The streaming source and sink are ordinary Sirius operators. They run on the same gpu_pipeline_executor, share the same worker pool, and follow the same hint protocol as every other operator. What makes them "streaming" is only what their input and output connect to.

Why "ordinary operators" matters

No separate subsystem = less to reason about

The sink is the final operator of its pipeline, running inside a normal gpu_pipeline_task on the existing gpu_pipeline_executor — just like RESULT_COLLECTOR or MERGE_GROUP_BY terminate a pipeline today. All existing memory reservation, CUDA stream management, and task lifecycle machinery applies unchanged.

No dedicated thread pool = no contention

Compute and streaming share one worker pool. There is no second scheduler to contend with for GPU resources. nixl's own threads live in the Rust wrapper and never touch the engine's worker pool. The bounded channel is the only hand-off queue; the wrapper's threads never enter the scheduler.

The coalescing state is NOT a second queue The partitioned sink (#837, #838) keeps bounded per-destination coalescing state internally — small slices accumulate until a size or time threshold, then flush one combined batch. This state is part of the sink's accounted operator state, not an unbounded second queue. It is repository-visible, so accumulated slices remain accounted and spillable while they wait.
05 · Ownership & handles

Why the channel carries handles, not shared_ptrs

This is the most important invariant in the design. Getting it wrong means queued batches become unspillable — stranded GPU memory that the downgrade executor cannot see.

The core rule The channel carries exchange_batch_handle{batch_id, size_bytes} — not a shared_ptr<data_batch> and not a raw buffer pointer. The owner of record is always the shared_data_repository registered with the memory manager.

Why handles keep batches spillable

If the channel owned shared_ptr<data_batch>s, queued batches would have a reference from the channel that the downgrade executor can't see — the sweep walks the repository, not the channel. Batches would be invisible to the spill machinery: unspillable GPU memory sitting in a queue.

Because the channel only holds ids and the repository holds the data, a queued batch can be downgraded to HOST while waiting in the channel. The consumer's pop_data_batch_by_id() gets a HOST-tier batch; the task's prepare_for_processing brings it back to GPU before compute — the same self-heal path proven by SRC-14 and the sink's spill tests.

The zero-copy steal and use_count()==1

The sink must feed each output batch to nixl. The ideal path is a zero-copy steal: if the repository is the sole remaining owner (use_count()==1), the sink can take the underlying cudf::table without copying. This is only possible because the channel is not an owner.

If the batch is still shared (being broadcast to multiple peers, or still registered for potential spill), use_count()>1 and the sink must deep-copy — which is why §6 reserves a non-borrowable send-copy credit. The proposed data_batch::release_or_copy_table() (cuCascade PR #148) makes this choice at runtime.

The ownership invariant in one sentence

Invariant A batch's use_count() reflects only real owners. "Idle ⇒ spillable" and "free on last drop" are both unambiguous only because the channel never increments the count. Enforce the handle discipline in the channel type itself — do not let callers sneak in shared_ptrs.

07 · Backpressure

Pressure propagates backward — against the data flow

The bounded channel is not just a buffer. When a downstream CN slows down, that pressure propagates all the way back to the upstream nixl sender in a chain of seven steps. Step through them.

The pivot: admission is a task-creation condition Enqueuing to a channel is evaluated before a task is scheduled, not discovered when it runs. The sink overrides get_next_task_hint() so that a full output channel reports not-ready even with input waiting. The task creator simply stops creating sink tasks — no worker thread ever parks on a full channel. This is the "admission ≠ fullness" lesson from the source PR applied to the producer side: the hint is the gate, not the actual push.

Per-destination channels isolate slow receivers

The partitioned sink (#837, #838) gives each destination its own output channel. A single slow receiver backs up only its partition rather than head-of-line-blocking every destination. However: a persistently slow partition still eventually pressures shared input (the single input channel that feeds all destinations). That policy question — block, spill, or drop slow partitions — is open question #838.

Two existing throttles compose with channel backpressure GPU memory reservations block when the budget is exhausted, and the GPU executor dispatches through a bounded worker pool, so compute is naturally rate-limited even before a channel fills (reserve_before_dispatch via make_reservation in gpu_pipeline_executor.cpp). The channel mechanism is the third throttle; together they give end-to-end, cross-node flow control with a bounded in-flight working set.

Re-arming: the edge-triggered side of the coin

Task creation is edge-triggered — there is no continuous polling. When the wrapper pull()s a batch and frees a channel slot, it must re-schedule the sink so the hint is re-evaluated and task creation resumes. This is the symmetric operation to how a completed task re-schedules its downstream consumers today. Until #839 lands, the tests poll instead.

The re-arm race A push (or pop) can land exactly as the hint is being dropped. If the session fires schedule(op) in the on_push / on_pop callback, and the creation loop is simultaneously evaluating a WAITING hint that it's about to discard, the wake signal can be lost. The design must either hold the schedule call outside the lock (so the hint evaluates after the signal) or add a level-triggered backstop (polling at low frequency as insurance). StarRocks solves this with driver event observers + a polling backstop — the same shape is expected for #839.
08 · Open questions

What #839 must still answer

open · §4 / #839 Cross-CN EOS. close_input(stream_id) is in-process only today. In a distributed exchange, end-of-stream must travel across nixl/bRPC as a terminal marker — and a source must learn its sender count from the plan so it finalizes only after every upstream CN has signaled done. Fan-in routing (stream_id → channel) alone does not settle completion. Where the sender count comes from (#841 plan translation?) and how it wires to the session is the deepest open question.
open · #838 Backpressure policy. §4 describes how pressure propagates; still open: the channel bound/size, whether a full input channel blocks push() or spills the queued batch, and how a persistently slow destination's partition is kept from starving shared input.
open · #840 / §6 Shared memory budget. Option A (shared cuCascade manager) is recommended. How borrow/lifetime and reentrancy of a shared manager work across concurrent queries, and where cross-domain stream-sync points fall during a spill, are still open. Specifically: the staging-lease cycle deadlock, the reserved receive-staging floor, and the send-copy credit must all be sized and enforced.
open · §7 / #839 Re-arm race. The on_push / on_pop callbacks must fire outside the channel lock and schedule the source/sink — but the hint evaluation and the callback can race. The exact synchronization protocol (edge-triggered + level-triggered backstop) needs to be pinned down before the session is safe to ship under load.
open · §7 / #839 Sink → nixl ownership. data_batch::release_or_copy_table() (proposed cuCascade PR #148, not in tree) would let the sink steal zero-copy when use_count()==1 or deep-copy when shared. Until it lands, the sink must choose between giving up spill-eligibility (drop repo ref first) or always deep-copying (cost). The send-copy credit (§6, constraint 4) must be reserved for the copy path.
