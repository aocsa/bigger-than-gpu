03 · The loud part

Biggest structural gap

Same slogan, opposite control planes

BlazingSQL makes queries “bigger than GPU” by demoting intermediates after they exist (CacheMachine) and optionally rewriting the plan into kernel pipelines. Sirius does it by refusing to run a task until memory is reserved, then predicate-spilling idle batches until that reservation fits — with pipelines and a data-driven task creator as the execution fabric.

BlazingSQL “bigger than GPU”

Demote + decompose (plan-time)

  • CacheMachine demotion — addToCache keeps GPU if counters fit; else ORC via CacheDataLocalFile (v0.14: no host tier yet).
  • Plan-time kernel decomposition — transform_operator_bigger_than_gpu rewrites Sort → SortAndSample → Partition → Merge (and Aggregate trio).
  • Execution — thread-per-kernel, blocking pullFromCache, no reservations, no task unit.
Mid-metamorphosis @ v0.14.0 transform_operators_bigger_than_gpu is hard-coded false. Host tier enum slots exist; only GPU + LOCAL_FILE are built. The KT mature model (3 tiers, always-on PhysicalPlanGenerator) is the destination, not the tag.
Sirius “bigger than GPU”

Reserve + spill-to-fit (runtime)

  • reserve-before-dispatch — make_reservation() before a worker touches the task; history-corrected peak estimate.
  • predicate-driven downgrade_executor — demote idle repository batches until make_reservation_or_null succeeds; stop immediately.
  • data-driven task_creator — hint chain READY / WAITING_FOR_INPUT; deepest ready producer first.
  • pipelines at blocking ops — streaming fuse; JOIN / ORDER_BY / agg break meta-pipelines.
  • Fallback — create_plan() throw → DuckDB CPU plan stays; silent.
What not to confuse BlazingSQL’s dual path is an opt-in graph flag. Sirius’s dual path is a capability gate with silent CPU fallback. CacheMachine demotion ≠ downgrade_executor (push-time tier pick vs reservation-serving sweep). Plan-string Sort rewrite ≠ converter’s three-pipeline sample sort (same algorithm family, different when/how).

QUEST — pipelines shipped, scheduling next

QUEST is this repo’s CPU/Disk engine. It is not a third GPU stack on this page — it is where you practice Sirius ideas at CPU scale, with BlazingSQL TaskFlow DNA already in the wiring. Full plan: docs/dev/sirius-replication-plan.md. Guideline for “how it should feel”: docs/sirius.html.

What QUEST already shipped for pipelines

Phase 2 closed the BlazingSQL-shaped “one thread per operator forever” trap. Sirius’s idea — streaming ops fuse; blocking ops are the seam — is now the default QUEST path:

  • MetaPipeline::Build(Graph) — splits the operator DAG at blocking operators; streaming ops (scan / filter / project) append to the current pipeline.
  • Pipeline — ordered fused list: one worker runs scan→filter→project per batch instead of queueing between every node (~5× less per-batch overhead in the flagship microbench).
  • Barriers on EdgeConfig — Pipeline (streaming) and Full (consumer waits for producer pipeline to finish). Partial waits for phase 6 joins.
  • PipelineExecutor — default under Graph::Execute() / PreparedQuery; legacy thread-per-operator survives only as deprecated ExecuteLegacy().
  • Bridge already closed (phase 1) — CreateGraph + real TableScan/Filter/Project/Collector; unsupported nodes fall back to the callback engine (Sirius-style gate discipline at CPU scale). Out-of-core spill under a tiny budget is real for that path.

What remains — task scheduling (phase 3)

Pipelines alone are not Sirius’s execution fabric. Sirius mints work only when data exists: operators answer hints; a task_creator recurses to the deepest READY producer; a scheduler matches tasks to workers; reservations gate dispatch. BlazingSQL has none of that — only thread-per-kernel + blocking pulls — so phase 3 is Sirius-guided, not a BlazingSQL port.

  • Today in QUEST: PipelineExecutor still uses a one-worker-drains-one-pipeline loop. A Pipeline-barrier consumer can park in Pull() and occupy a worker — the documented ordering hazard.
  • Build next: GetNextTaskHint() / GetNextTaskInputData() on Operator; Task = {Pipeline*, DataBlockPtr}; TaskCreator recursion; TaskScheduler over a fixed jthread pool inside PreparedQuery (rewrite-in-place of the executor).
  • Invariants to steal from Sirius: mark task created before popping input; a consumer without input is a non-created task, never a blocked thread; live SetFlowControl must re-arm the creator (wake contract from the DSL design).
  • Done when: correct results on a 4-worker pool; Full-barrier ordering holds; throughput scales with workers on multi-pipeline plans. Read first: Sirius task_creator.cpp + task_scheduler.cpp (paths in the replication plan).
Why not copy BlazingSQL here? v0.14 graph.execute() never invented a task unit. Closing the scheduling gap means studying Sirius’s hint chain (docs/sirius.html · tasks), then building the CPU-scale equivalent — same learning rule as the rest of the replication plan.

Phase 3 — Data-driven tasks + scheduler
Sirius idea · hint chain

Replace drain-one-pipeline with task-granular scheduling inside PreparedQuery. No BlazingSQL analogue — see the phase-3 notation in the replication plan.

Study: Sirius tasks section; then implement TaskCreator / TaskScheduler per the plan’s build list.

Phase 4 — Memory reservations
Sirius idea · reserve before dispatch

Tasks must MakeReservation(estimated_peak) before run. Fix accounting first (real batch bytes; macOS sysctl(HW_MEMSIZE)). History ring corrects estimates. Failed reservation requeues (and later triggers phase-5 downgrade).

Why after 3: reservations gate tasks, not threads. BlazingSQL’s counter demotion at addToCache is a different control plane — useful contrast, wrong template.

Study: Sirius reservation manager (47-line header) + executor reserve→dispatch path in docs/sirius.html memory section.

Still only 3 of 19 operators wired for end-to-end queries (Scan, Filter, Projection). Heavy ops (agg / sort / join) remain phase 6 — after scheduling and reservations exist so each task stays bounded. Do not deepen the callback engine; deepen the graph path.

06 · Learn by doing

Roadmap — close the design gaps with your hands

Eight phases ordered by learning value for someone who knows BlazingSQL and is reading Sirius. QUEST-specific pipeline / scheduling study lives in QUEST study; file paths below are from the companion docs / replication plan.

Read the two gates side by side

Exercise · no code

BlazingSQL: runQuery fork (evaluate_query vs execute_plan, use_execution_graph). Sirius: OnFinalizePrepare → sirius_physical_plan_generator::create_plan() — translate or throw, CPU plan stays.

Do: Write one page: “What does each engine do when the GPU path cannot represent the plan?” Then skim sirius_optimizer_extension.cpp and BlazingSQL engine.cpp:118-124.

Trace one ORDER BY end-to-end

Exercise · both engines

BlazingSQL: distributed_sort (OrderBy.cpp) and the gated SortAndSample → Partition → Merge trio. Sirius: converter’s three-pipeline sample sort after sirius_meta_pipeline::build().

Do: Draw the stages (sample → pivots → partition → merge). Mark which are plan-time rewrites vs runtime converter injections. Note v0.14 transform is off.

Ports & buffers: CacheMachine vs shared_data_repository

Exercise · data plane

BlazingSQL: port → CacheMachine + WaitingQueue; addToCache / pullFromCache. Sirius: repositories keyed (operator_id, port_id) only at pipeline boundaries; mid-pipeline is fused.

Do: Read CacheMachine.h demotion loop vs Sirius repository insert sites. Answer: where can idle data sit to be spilled?

Pipelines vs thread-per-kernel

Exercise · execution fabric

BlazingSQL graph: one BlazingThread per kernel, forever. Sirius: streaming ops append; blocking ops sink a pipeline and source the next (sirius_meta_pipeline.cpp).

Do: For scan→filter→project→sort, count threads/tasks each engine would create. Then read the converter’s seven phases at a skim level (don’t memorize — learn why each exists).

The hint chain (Sirius-only leap)

Exercise · scheduling

BlazingSQL has no task creator — kernels block on queues. Sirius task_creator: get_next_task_hint() → READY or WAITING_FOR_INPUT; recurse to deepest ready producer (task_creator.cpp).

Do: Walk get_operator_for_next_task() on paper for a two-pipeline join. QUEST readers: this is replication-plan phase 3.

Reservations vs counter demotion

Exercise · memory control plane

BlazingSQL: post-produce tier pick with usedMemory counters (75% free GPU). Sirius: sirius_memory_reservation_manager + make_reservation() before dispatch; adaptor charges cuDF allocs.

Do: Contrast “spill because the cache is full” with “spill until this reservation fits.” Read the 47-line reservation header first.

Predicate downgrade vs addToCache ORC

Exercise · spilling semantics

Sirius downgrade_executor: request_downgrade(predicate), idle batches, stop when reservation succeeds. BlazingSQL: detached ORC write on pressure; host tier missing at v0.14.

Do: List correctness properties (atomicity, over-freeing, who is on the hot path). Note Sirius batch lock states idle / read_only / mutable_locked.

Aggregate / join decompositions & expressions

Exercise · operators + AST

Both engines partition/merge heavy ops (Blazing Aggregate* trio; Sirius MERGE_* / PARTITION around joins). Expressions: BlazingSQL interops interpreter vs Sirius AST + pluggable strategies.

Do: Pick GROUP BY or JOIN; map stages across engines. Optional QUEST: heritage map in docs/dev/graph-builder-dsl.md §11 (CacheMachine → BatchHolder).
